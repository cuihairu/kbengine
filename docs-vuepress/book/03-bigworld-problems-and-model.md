# 3. KBEngine 系统全景

> 如果上一章回答的是“为什么会形成 BigWorld 这套模型”，这一章回答的就是“KBEngine 在这个模型上具体采用了什么结构，又做了哪些取舍”。

## 3.1 本章核心问题

- KBEngine 和 BigWorld 的关系应该怎么理解？
- 五类进程的职责边界是什么？
- 进入源码阅读前，必须先记住哪几条系统边界？

## 3.2 先给结论：KBEngine 不是照搬 BigWorld，而是在同一模型上做开源化取舍

最容易出现的两种误解是：

- 误解一：KBEngine 就是 BigWorld 的“简化版复刻”
- 误解二：KBEngine 是完全独立的一套 MMO 服务端模型

更准确的说法应该是：

- KBEngine 明显继承了 BigWorld 的核心运行模型
- 但它在工程组织、技术栈、实现细节和开源可维护性上做了自己的选择

所以理解 KBEngine 的最好方式不是“把 BigWorld 忘掉”，而是：

- 先承认它们共享一套深层模型
- 再看 KBEngine 在哪些地方做了变形与简化

## 3.3 KBEngine 的五类进程

从系统地图上看，KBEngine 至少可以拆成五类进程：

### 接入层

- `LoginApp`

负责：

- 第一跳接入
- 登录分发
- 把客户端导向正确的 `BaseApp`

### 逻辑层

- `BaseApp`

负责：

- 玩家长期逻辑主体
- `Proxy`
- 客户端会话绑定
- Base 实体生命周期
- 与 DB、Cell 的协作

### 空间层

- `CellApp`

负责：

- 实时空间运行
- `Space / AOI / Witness`
- `real / ghost`
- 空间内方法调用与同步

### 持久化层

- `DBMgr`

负责：

- 账号 / 实体基础状态查询
- 持久化、恢复、删除
- 在线 / 离线边界管理

### 管理与外围层

- `BaseAppMgr`
- `CellAppMgr`
- `Machine`
- `Interfaces`
- `Logger`
- `Bots`

它们不一定直接承载玩家主逻辑，但决定了整个系统能否被调度、观察、接入外部系统和测试。

## 3.4 玩家主线应该怎样映射到这些进程

如果你想建立最实用的系统图，最好先记住这一条玩家主线：

1. 客户端先到 `LoginApp`
2. 登录状态与账号基础信息查询会经过 `DBMgr`
3. 真正长期持有玩家逻辑的是 `BaseApp`
4. 玩家进入世界后，实时空间态交给 `CellApp`
5. 写库、恢复、删除等持久化动作仍然通过 `DBMgr` 收束

这条主线非常重要，因为后面多数源码走读其实都是它的局部展开。

## 3.5 KBEngine 对 BigWorld 的几个关键取舍

如果只看高层模型，KBEngine 和 BigWorld 很像；如果落到工程实现，就能看到一些很实际的取舍。

### 更强调 Python 脚本驱动

KBEngine 里很多核心行为都直接暴露到 Python 层，脚本驱动感更强。这样做的好处是：

- 开发体验更直接
- 业务层调整更快

代价是：

- C++ / Python 边界理解成本更高
- 运行时行为分散在两层之间

### 更偏开源工程现实

BigWorld 的很多设计来自商业引擎和成熟产品背景，而 KBEngine 需要在开源社区环境下权衡：

- 可读性
- 可部署性
- 跨平台维护
- 第三方依赖现实

所以你经常会看到它保留模型核心，但实现上更直接、也更“工程化”。

### 在一些地方更偏“可用而非完美”

这不是贬义，而是开源项目常见现实。很多实现明显是围绕：

- 先把完整运行链打通
- 再在关键点做性能和协议优化

而不是每个子系统都打磨成学术式完美抽象。

## 3.6 进入源码前必须先记住的四条系统边界

如果不先建立边界意识，后面读代码会一直把职责看混。

### 接入边界

`LoginApp -> BaseApp`

问题本质是：

- 第一跳接入
- 第二跳会话真正落地

### 逻辑边界

`BaseApp -> CellApp`

问题本质是：

- 长期逻辑主体
- 实时空间主体

### 持久化边界

`Base / Cell -> DBMgr`

问题本质是：

- 运行态
- 持久态

### 管理边界

`*Mgr / Machine -> 业务组件`

问题本质是：

- 调度、注册、发现
- 真正逻辑执行

## 3.7 为什么这四条边界对源码阅读特别重要

后面你会遇到很多“看起来都像处理玩家”的代码，但它们其实并不是一回事。

例如：

- 登录成功回客户端地址，是接入边界问题
- `Proxy` 绑定新客户端，是逻辑边界问题
- 创建 Cell 实体，是逻辑向空间边界推进
- `writeToDB`，是运行态向持久态边界收束
- `onRegisterNewApp`，则是管理边界上的集群组织问题

一旦边界感清楚，同一个“玩家行为”在不同组件里就不会再显得杂乱。

## 3.8 为什么定位和架构必须放在一起讲

这也是这次重排目录里最重要的一点。

如果只先讲“KBEngine 的来源、定位与取舍”，但不紧接着讲它的系统全景，读者会得到一堆抽象判断，却还不知道：

- 这些取舍最后落在哪些组件上
- 哪些是主线、哪些是支撑层

反过来，如果只讲架构图，不讲它和 BigWorld 的关系，读者又容易把这套模型误当成：

- 某个项目随手拆出来的服务图

所以定位和系统地图必须在同一章里收束。

## 3.9 一张足够实用的脑内系统图

建议读者先在脑中固定这一张图：

`Client -> LoginApp -> BaseApp -> CellApp`

与此同时：

- `DBMgr` 在侧面参与账号状态、实体恢复、写库与删除
- `BaseAppMgr / CellAppMgr / Machine` 在更外层组织整个集群
- `Interfaces / Logger / Bots` 提供外部接口、日志和测试能力

后面你在任意源码文件里迷路时，都可以先问自己：

- 这段代码属于这张图里的哪一层？

## 3.10 本章小结

这一章最重要的结论是：

- KBEngine 和 BigWorld 共享一套核心 MMO 运行模型
- KBEngine 在开源工程现实下对这套模型做了自己的实现取舍
- 系统至少可以拆成接入、逻辑、空间、持久化、管理五类进程
- 进入源码前，必须先记住接入、逻辑、持久化、管理四条边界

当这张系统地图建立起来后，后面再读启动、EntityDef、RPC、Space、DB 等章节，读者就不再是在一堆零散组件之间来回跳，而是在一张稳定框架图上逐步填细节。
