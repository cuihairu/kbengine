# 2. BigWorld：问题、模型与核心概念

> 这一章不打算把 BigWorld 写成一段产品史，而是把后面理解 KBEngine 所必需的那部分背景一次讲完。目标只有一个：让读者先建立“为什么会长成 Login / Base / Cell / DB 这套模型”的心智框架。

## 2.1 本章核心问题

- 大规模在线世界到底遇到了哪些传统游戏服务器很难承受的问题？
- 为什么这些问题最后会逼出 `Login / Base / Cell / DB` 这类分工？
- `Entity / Proxy / Space / Witness / Ghost` 这些概念在同一个运行模型里各自扮演什么角色？

## 2.2 先从问题出发，而不是先背术语

BigWorld 一系技术路线真正要解决的，不是“服务器怎么写得更优雅”，而是几类很具体的工程约束：

- 在线人数很高，单进程难以稳定承载所有玩家状态
- 场景内位置、可见性、移动和战斗是高频实时问题
- 场景外账号、背包、任务等逻辑又更接近长期状态管理问题
- 数据既要持久化，又不能让数据库成为实时状态来源
- 玩家会掉线、重连、切图、跨进程迁移，在线状态不能一断就全丢

把这些问题放在一起看，就会发现：

- “一个玩家对象”并不足以表达所有运行态
- “一个服务器进程”也不足以承载整个世界

所以 BigWorld 的价值，不在于发明了一堆术语，而在于把这些约束组织成了一套能长期运行的模型。

## 2.3 为什么会形成 `Login / Base / Cell / DB`

如果把问题继续拆开，就会自然推出几种不同职责：

### 接入问题

客户端第一跳接入、认证、分发，不应该直接和玩家长期运行态绑死，于是有了：

- `Login`

### 长期逻辑问题

账号、Proxy、脚本业务主体、客户端会话绑定，需要一个长期持有玩家逻辑对象的地方，于是有了：

- `Base`

### 实时空间问题

位置、AOI、移动、可见性、空间内实时交互，不适合放进同一套长期逻辑上下文里，于是有了：

- `Cell`

### 持久化问题

数据库应该负责冷状态、恢复状态和在线元信息，而不应该直接变成实时世界的一部分，于是有了：

- `DB`

所以 `Login / Base / Cell / DB` 并不是拍脑袋拆服务，而是被四类问题自然塑造出来的分工。

## 2.4 为什么 Entity 一定会出现“多侧表示”

一旦你接受了 Base / Cell 分离，就会立刻遇到一个问题：

- 一个玩家到底算一个实体，还是两个实体？

BigWorld 一系给出的答案是：

- 语义上它仍然是“同一个实体”
- 运行时上它可以有不同侧的表示

于是就有了：

- Base Entity
- Cell Entity
- Client 侧表现

这背后的核心思想是：

- 一个游戏对象不是只能有一个物理驻留点
- 不同侧分别承载它的不同职责

这也是为什么后面你会在 KBEngine 中不断看到：

- Base 侧有一份实体
- Cell 侧有一份实体
- 客户端拿到的是它的网络表现

## 2.5 `Proxy` 为什么特殊

在这一整套模型里，`Proxy` 不是普通实体概念，而是把“玩家在线连接”带进实体模型的关键对象。

它最重要的价值是：

- 它既是实体
- 又是客户端会话的入口

也就是说：

- 一个玩家不只是数据库里的一条记录
- 也不只是世界里的一个坐标点
- 他还是一个受客户端控制、可能重连、可能挤号、可能切换控制权的在线会话对象

`Proxy` 就是这层语义的集中承载点。

## 2.6 `Space`、`Cell`、`AOI`、`Witness` 为什么是核心，不是附属功能

普通服务端直觉里，很容易把“可见性”理解成一个附加模块。但在 BigWorld 一系里，它是核心问题之一。

原因很简单：

- 世界很大
- 实体很多
- 客户端不可能也不应该收到整个世界

于是系统必须回答：

- 当前这个客户端到底该看到谁？

这就逼出了几层关键结构：

- `Space`
  世界运行空间
- `Cell`
  空间运行和承载的最小单元之一
- `AOI`
  可见范围判定机制
- `Witness`
  把“可见范围变化”变成真正客户端同步的控制器

所以 `Witness` 不是“方便一点的观察者类”，而是大规模在线世界里客户端可见性控制的核心执行点。

## 2.7 `Ghost` 为什么存在

一旦空间和 Cell 可以分布式运行，你又会碰到另一个问题：

- 某个实体真实逻辑在别的 Cell 上，但本地又需要知道它的存在和部分状态，怎么办？

于是就有了：

- `Ghost`

它的核心用途不是“复制一份实体玩玩”，而是：

- 在分布式空间运行中，为远端真实实体提供局部可见和协作副本

这也是为什么后面在 KBEngine 里，`real / ghost` 会频繁出现在：

- AOI
- teleport
- 跨 CellApp 路由
- 远程方法调用

这些地方。

## 2.8 把这些概念放回同一个运行模型

如果把前面的对象放回一张统一模型图，可以这样理解：

1. 客户端先通过 `Login` 接入
2. 玩家长期逻辑实体停在 `Base`
3. 玩家进入世界后会有对应的 `Cell` 侧实体
4. 若该玩家受客户端控制，则通过 `Proxy` 和客户端绑定
5. 玩家所在 `Space` 决定它处于哪个世界上下文
6. `Witness` 负责把周围实体的可见性变化同步给客户端
7. 若实体跨 Cell 运行，则 `Ghost` 帮助维持分布式空间协作
8. `DB` 负责持久化、恢复和在线元信息，而不是实时世界本身

这样你就会发现，这些术语并不是散落的定义，而是同一个系统模型里的不同支点。

## 2.9 为什么这套模型今天看起来仍然成立

即使技术栈变了，BigWorld 一系模型今天看起来仍然有生命力，原因也很直接：

- 大规模在线状态依然需要分层
- 实时空间问题依然和长期业务问题不同
- 客户端可见性依然不能靠全量广播解决
- 持久化依然不应该直接充当实时状态主源

所以 KBEngine 虽然在实现、开源工程边界和技术细节上有自己的取舍，但它继续沿用这套模型，并不是历史包袱，而是这些问题本身还没消失。

## 2.10 本章小结

这一章最重要的收获应该是：

- BigWorld 模型首先是问题驱动的，不是术语驱动的
- `Login / Base / Cell / DB` 是四类不同问题的自然分工
- 实体必须允许多侧表示，才能支撑长期逻辑和实时空间分离
- `Proxy / Space / Witness / Ghost` 都不是附件，而是运行模型核心部件

把这层心智模型建立起来之后，再去读 KBEngine 的整体架构和源码实现，很多设计就不会显得突兀。
